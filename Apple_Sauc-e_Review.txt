Kathleen Schechner2026-01-30 2:44 AM
Hello,
Thank you for the detailed crash logs and guidance. We have identified and resolved the issue affecting all three applications.
Issue Identified:
The crashes were caused by RevenueCat's native module initialization occurring too early in the app lifecycle, before the React Native bridge was fully ready. This triggered a native ObjC exception during TurboModule invocation, resulting in SIGABRT crashes on launch.
Resolution Applied:
We have moved RevenueCat configuration to post-launch initialization using a delayed useEffect pattern. This allows the app to mount successfully before initializing payment infrastructure. The apps now launch cleanly, and RevenueCat initializes safely in the background after the bridge is ready.
Technical Details:

Modified initialization to use setTimeout wrapper (500ms delay)
Added proper cleanup handlers
Maintained graceful degradation if RevenueCat initialization fails
Apps continue functioning normally regardless of payment system status

New Builds Submitted:

CATSUP 369: Version 1.0.3 (Build 4)
BBQE (3,6,9): Version 1.0.3 (Build 4)
RELISH: Version 1.0.3 (Build 4)

All three applications have been tested and launch without crashes. The delayed initialization pattern resolves the timing issue identified in your crash reports.

**Subject: CATSUP (3,6,9), BBQE (3,6,9), RELISH (3,6,9) - Updated Architecture & Security**

Dear Apple Review Team,

We are resubmitting three applications (CATSUP (3,6,9), BBQE (3,6,9), RELISH (3,6,9)) with significant security improvements.

**Previous Feedback:** Your team correctly identified that API credentials should not be embedded in the iOS client. We have implemented this feedback completely.

**What We Changed:**

All three applications now use a secure backend infrastructure (Railway) for all API calls:
- CATSUP (3,6,9): Claude API calls now routed server-side
- BBQE (3,6,9): RapidAPI threat database queries now routed server-side  
- RELISH (3,6,9): Claude API calls now routed server-side

The iOS apps contain zero sensitive credentials. All requests are made to our verified backend at `https://sauc-e-backend-production.up.railway.app`

RevenueCat integration uses only the public API key (as intended by RevenueCat).

**Security Model:**
- Device: Calls backend with user question/email
- Backend: Uses hardcoded API credentials to call third-party services
- Backend: Returns clean results to device
- Device: Never sees API credentials

**Architecture Benefits:**
- Zero exposed secrets in app bundle
- Easier credential rotation (backend update only)
- Audit trail for all API calls
- Rate limiting at backend level
- Improved privacy

We appreciate your guidance on best practices. This architecture reflects industry standards for mobile app security.

Submitting for your review.

Thank you for reviewing RELISH v3.1.3.
This build ships with server-side diagnostic instrumentation specifically scoped to the in-app purchase flow that has been flagged in prior review rounds. The purpose of this build is to establish a common data record between your review session and our engineering logs, so that the specific failure condition observed on the review device can be identified from our side.
If the "Upgrade to Peak" button behaves unexpectedly on your review device, please follow this procedure:

From the main screen, tap "Upgrade to Peak · 10 free left."
If a "Subscription Unavailable" alert appears, tap Show Diagnostic.
Alternatively, scroll to the bottom of the paywall modal and tap the "Paywall not working? Tap here to show diagnostic" button.
The diagnostic panel will display the complete state of the subscription system at the moment of your test, including the Session ID at the bottom of the panel.
Please include the Session ID in your response to this submission. This Session ID permits us to correlate your review session with the corresponding server-side log on our backend and identify the specific condition producing the failure.

The diagnostic payload is transmitted to our server automatically when the panel is opened, so the data will be available on our side regardless of whether the reviewer chooses to tap "Send to Developer."

We have not been able to reproduce the failure condition on any of our test devices or sandbox accounts. The present build is our standard engineering procedure for diagnosing an issue that cannot be reproduced in the local environment: instrument the remote environment and correlate logs.

# RELISH v3.2.1 — Apple Review Notes

**Subject line for internal routing:** RELISH v3.2.1 — Diagnostic Fix — Session ID Required

---

## What Changed

v3.2.0 shipped with diagnostic instrumentation. One UI entry point wasn't rendering when offerings returned empty.

Fixed: diagnostic banner now shows whether offerings fail *or* return zero packages. Reviewer always has a "Show Diagnostic" button.

## What You'll See

1. Tap "Upgrade to Peak · [N] free left"
2. Paywall opens
3. If anything goes wrong with products, an error banner appears with a **"Show Diagnostic Details"** button
4. Tap it → diagnostic panel opens → Session ID appears at bottom
5. Include that Session ID in your response to us

That's it. One tap, one number, problem solved on both ends.

## If It Works Fine

Great. Tap the paywall title three times → diagnostic panel opens → confirms everything loaded correctly.

---

## Session ID Format

`rlsh-<timestamp>-<6 chars>`

Paste it in your response. We correlate it with our backend logs and identify exactly what your device saw.

Three sister apps live on the web (sauc-e.com, cats-up.app, catsup.net) processing payments via PayPal/Stripe/Square. We rebuilt RevenueCat from scratch before this submission. We cannot reproduce the v3.1.x failure locally. v3.2.1 is the instrumentation we use to see what your device sees.
